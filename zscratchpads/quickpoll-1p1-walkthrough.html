The short version

🧭
One LTI 1.1 launch is one signed web form
Canvas fills in a form, signs it, and your browser sends it to your app. Your app checks the signature. That is the whole protocol.
  • Canvas and your app both know a shared secret. The secret never travels over the network.
  • Canvas runs a math function over the form fields and the URL, using the secret. The result is oauth_signature.
  • Your app runs the same function on what it received. A match means Canvas sent the form and nobody changed it.
  • No match means reject the launch.
The app now checks every launch. It looks up the consumer key, checks the signature, then checks the timestamp and nonce. Any failure gets a 401. A launch that passes saves the person and the course. A verified launch also starts a session, so the next page knows who you are and whether they may create polls. A verified launch then redirects to the poll page. An instructor or a TA creates polls there. Everyone in the course sees them and votes once per poll. A person sees the counts after voting. A poll creator always sees them. The specs pass. Grade passback is next.

Read the code

Open each block in turn. The request path is the controller plus three small service classes.

1. config/routes.rb (lines 4 to 7): the entry point 
namespace :lti do
  get  "config", to: "configuration#show", defaults: { format: :xml }, as: :configuration
  post "launch", to: "launch#create", as: :launch   # line 6: the launch lands here
end

namespace :lti adds /lti to the URL and Lti:: to the controller name. So post "launch" becomes POST /lti/launch and Lti::LaunchController#create. The second route, GET /lti/config, serves the XML.

2. app/controllers/lti/base_controller.rb: shared setup 
class BaseController < ApplicationController
  skip_forgery_protection          # Canvas cannot send a Rails CSRF token
  before_action :allow_framing   # before, not after: see Gotchas

  private

  def allow_framing
    response.headers.delete("X-Frame-Options")   # Rails blocks iframes by default
  end

  def current_lti_user
    @current_lti_user ||= LtiUser.find_by(id: session[:lti_user_id])
  end

  def current_lti_context
    @current_lti_context ||= LtiContext.find_by(id: session[:lti_context_id])
  end

  def can_create_polls?
    session[:can_create_polls] == true      # a missing value means false
  end

  def require_launch                 # a before_action for pages that need a launch first
    unless current_lti_user && current_lti_context
      reset_session
      render plain: "Launch required.", status: :unauthorized
    end
  end
end

Rails normally rejects a POST that lacks its own CSRF token. That would block every launch. The signature replaces the CSRF token as the proof of origin. Skipping CSRF is safe because LaunchController checks the signature before it does anything.

3. app/controllers/lti/launch_controller.rb: check, then save 
class LaunchController < BaseController
  before_action :verify_launch          # runs the three checks first

  def create                           # only reached if every check passed
    records = Lti1p1::LaunchRecords.new(consumer: @consumer, params: request.request_parameters)
    if records.call
      reset_session                                   # a fresh session on every launch
      session[:lti_user_id]    = records.user.id      # ids only, never names or params
      session[:lti_context_id] = records.context.id
      session[:can_create_polls] = Lti1p1::Roles.new(request.request_parameters).can_create_polls?  # the answer, not the role strings
      redirect_to lti_polls_path, status: :see_other   # the iframe now shows the poll page
    else
      Rails.logger.warn("[lti launch] rejected: #{records.error}")
      render plain: "Launch failed.", status: :bad_request
    end
  end

  private

  def verify_launch
    @consumer = LtiConsumer.find_by(consumer_key: request.request_parameters["oauth_consumer_key"])
    return reject(:unknown_consumer) if @consumer.nil?

    verifier = Lti1p1::SignatureVerifier.new(
      method: request.method,
      url: "#{Rails.configuration.x.public_base_url}#{request.fullpath}",
      params: request.request_parameters,
      secret: @consumer.shared_secret
    )
    return reject(:bad_signature) unless verifier.valid?

    guard = Lti1p1::ReplayGuard.new(consumer: @consumer, params: request.request_parameters)
    reject(guard.error) unless guard.accept?
  end

  def reject(reason)
    Rails.logger.warn("[lti launch] rejected: #{reason}")
    render plain: "Launch rejected.", status: :unauthorized
  end
end

The session is a signed, encrypted cookie. After a verified launch it holds two ids. A later request reads them back through current_lti_user. reset_session comes first, so a cookie planted before the launch dies (session fixation). A before_action that calls render ends the request. So a failed check answers 401 and create never runs. The order matters: the signature check comes before the guard, so a forged launch cannot save a nonce. The 401 text is the same for every failure. The reason goes to the log only, and never the launch values (student data).

4. The three services in app/services/lti1p1/
SignatureVerifier
new(method:, url:, params:, secret:), then valid?. It builds the base string, signs it, and compares with secure_compare. normalized_url lowercases the scheme and host, drops a default port, and drops the query. all_params merges the URL query with the body and counts an identical pair once.
ReplayGuard
new(consumer:, params:), then accept?. It checks the params exist, the timestamp is within 300 seconds either way, and the nonce is new. Then it inserts the nonce. The unique index decides a race between two launches.
LaunchRecords
new(consumer:, params:), then call. It needs user_id and context_id. It finds or creates the user and the course in one transaction. A blank name or title never erases a saved one.

All three take plain Ruby arguments, not the Rails request. That is why each has its own spec file and none needs a browser.

5. app/controllers/lti/configuration_controller.rb and the XML template 
def show
  base = Rails.configuration.x.public_base_url   # "http://quickpoll-1p1.inseng.test"
  @launch_url = "#{base}/lti/launch"
  @placement  = "course_navigation"
  render formats: :xml
end

The template fills <blti:launch_url> and the placement URL from those values. Canvas reads the XML once, at install time. PUBLIC_BASE_URL comes from docker-compose.yml, through config/initializers/lti.rb.

6. config/initializers/lti.rb: why the base URL is configured 
Rails.configuration.x.public_base_url = ENV.fetch("PUBLIC_BASE_URL", "http://localhost:3000")

Canvas signs the exact URL it posts to, including http versus https. A proxy can change the scheme before Rails sees it, so request.url is unreliable. The controller builds the URL from this setting instead.

The text secret. Canvas and your app both store it. The consumer key (key) tells your app which secret to use.

The exact launch URL, with no query string. The scheme and host count.

Check your understanding

Why does Test 1 become Test%25201?

Encoding the space gives %20. The second encode turns the % into %25, so %20 becomes %2520.

A proxy changes https to http before Rails sees the request. Which URL should the verifier use?

The one built from PUBLIC_BASE_URL. Canvas signed the https URL. If you rebuild it from request.url, the scheme differs, and every valid launch fails.

Someone replays a valid captured launch 10 minutes later. What stops it?

The timestamp check stops it: the launch is older than 5 minutes. Inside the 5 minutes, the nonce check stops it, because the first launch already saved that nonce. Both are in Lti1p1::ReplayGuard, and both run after the signature check.

Vocabulary

oauth_consumer_key
A public name for the Canvas side of the connection. Yours is key. It selects the secret.
shared secret
The private text both sides know. Yours is secret. Never sent in a request.
oauth_nonce
A random string, new on every launch. Your app records it so a copy of the launch cannot run twice.
oauth_timestamp
Seconds since 1970 when Canvas signed the form. Old timestamps are rejected.
context_id
The course. The same on every launch from that course.
resource_link_id
One placement of the tool. In course navigation it equals context_id. On an assignment it differs.
user_id
An opaque 40-character id for the person. Use this one. custom_canvas_user_id is Canvas's database number.
placement
Where in Canvas the link lives. Yours: course_navigation.
tool_consumer_instance_guid
Which Canvas installation sent the launch. A user_id is only unique inside one guid.
replay
Sending a copied launch again. The signature stays valid, so the timestamp and nonce checks stop it.
session
A cookie the browser sends back on every request. It lets the tool remember who launched. A verified launch starts one and stores the user id and the course id.
roles / ext_roles
Two launch fields that say what the person is in the course. Short names like Instructor, or URNs like urn:lti:role:ims/lis/Instructor. Read both.
303 See Other
A redirect after a POST. It tells the browser to load the next page with a GET. The launch and the poll form both use it.
session fixation
An attacker plants a session cookie, then waits for the victim to sign in. A fresh session on every launch (reset_session) stops it.

Gotchas we already hit

A param can arrive twice. With "OAuth Compliant" off, Canvas leaves ?placement=... on the URL and also copies it into the body. It signs the value once. A literal reading of RFC 5849 counts it twice and fails. One spec covers this. Fix it by treating identical name and value pairs as one.
Roles come in two shapes. A teacher sends Instructor. An admin who is not enrolled sends URNs like urn:lti:instrole:ims/lis/Administrator, and only ext_roles lists Instructor. Read the text after the last / in each entry. A real TA sends TeachingAssistant in roles and also Instructor in ext_roles, so a TA counts as an instructor. The poll pages ask can_create_polls?.
Forgery protection: off for the launch, on for the poll form. BaseController skips it, because Canvas posts the launch from another origin and the signature is the proof. The poll form is a normal form from this app, so PollsController turns it back on with protect_from_forgery with: :exception. Rails' test setup disables it, so one spec switches it on. A live check showed the token works inside the Canvas iframe.
Find a record through the session's course. current_lti_context.polls.find(id) answers 404 for a poll in another course. Poll.find(id) would let a person vote in any course by guessing an id. A spec checks this.
Views cannot call private controller methods. can_create_polls?, current_lti_user, and current_lti_context are private in BaseController. A line helper_method ... makes them callable from a view.
The test environment. The container sets RAILS_ENV=development. spec/rails_helper.rb now forces test, so plain rspec in the container uses the test database. Without that, rspec hit the dev database and its seeded consumer.
to_query encodes a space as +. OAuth needs %20. Encode each name and value with the same function you use for the URL. This one bug failed every captured launch, because they contain spaces.
Use request.request_parameters, not params. params adds controller, action, and the query keys. Canvas never signed those, so the signature fails.
A failed before_action skips every after_action. The 401 pages kept X-Frame-Options, and Canvas would not show them. Removing the header in a before_action fixes it.
Session cookies in an iframe. Locally it works, because Canvas and the tool share the inseng.test domain. In production they are different sites, and browsers block third-party cookies. Safari blocks them now. It needs same_site: :none and secure: true, and still may fail. Stage 7 comes back to this.
The json gem. Version 3.x breaks Rails 8.0.5.2 with unknown keyword: quirks_mode. The Gemfile pins json < 3. Remove the pin after a Rails upgrade that fixes it.
Iframe header. Rails sends X-Frame-Options: SAMEORIGIN by default. The browser would refuse to show the page inside Canvas. BaseController removes it.
Real data. A launch holds names, emails, and user ids. That is student data under FERPA. Use fake users in a test course, and keep real launches out of shared docs and fixtures.
